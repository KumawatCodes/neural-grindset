## SECTION 1 — Hive Architecture (Viva Theory)

### What is Hive?

- Data warehouse tool built on top of Hadoop
- Allows SQL-like queries (HiveQL) on data stored in HDFS
- Hive does NOT store data — data lives in HDFS
- Hive translates HiveQL → MapReduce / Tez / Spark jobs
- Created at Facebook for analysts who know SQL but not Java
- Designed for batch processing — NOT real-time queries

### Components of Hive Architecture

```
Client (CLI / JDBC / Web UI)
        |
      Driver
        |
    Compiler  <------>  Metastore (MySQL/Derby)
        |
    Optimizer
        |
    Executor
        |
  Execution Engine (MapReduce / Tez / Spark)
        |
      HDFS (actual data)
```

**Driver:**

- Entry point for all HiveQL queries
- Manages query lifecycle: parse → compile → optimize → execute
- Maintains session handles

**Compiler:**

- Parses HiveQL query
- Checks table/column names against Metastore
- Generates logical plan → physical plan (DAG of jobs)

**Optimizer:**

- Optimizes physical plan
- Techniques: predicate pushdown, column pruning, join reordering

**Executor:**

- Submits the optimized plan to MapReduce/Tez/Spark
- Jobs read from HDFS, process data, write results back to HDFS

**Metastore:**

- Stores all metadata: table names, column names, data types, HDFS paths, partition info, bucket info
- Backed by: MySQL (production), Apache Derby (testing/default)
- Without Metastore: Hive does not know what tables exist or where data is

**HDFS:**

- Stores actual table data as files
- Default warehouse path: `/user/hive/warehouse/`

### Schema on Read vs Schema on Write

- Traditional RDBMS: schema enforced on WRITE (data validated when inserted)
- Hive: schema enforced on READ (data stored as raw files, schema applied when querying)
- Advantage: flexible — load any file, define schema later
- Disadvantage: no write-time validation

### Hive vs RDBMS (Most Asked Viva Question)

|Feature|Hive|RDBMS|
|---|---|---|
|Data storage|HDFS|Local disk|
|Query language|HiveQL|SQL|
|Processing|MapReduce/Tez (batch)|In-process (real-time)|
|Schema|Schema on read|Schema on write|
|Updates/Deletes|Very limited|Full support|
|Latency|High (seconds to minutes)|Low (milliseconds)|
|Designed for|Large-scale analytics|OLTP transactions|
|Joins|Supported but slow|Fast with indexes|

### Why is Hive Slower than Traditional Database?

- Every query is converted to MapReduce/Tez job
- MapReduce has high startup overhead (JVM launch, HDFS read)
- No indexes (by default) — full table scan for every query
- Data stored in HDFS (distributed) — network overhead
- Designed for throughput, not latency

### What if Small Files Increase in Hive?

- HDFS is optimized for large files (128MB+ blocks)
- Too many small files → too many HDFS blocks → NameNode memory overload
- Each small file = one Map task → too many Mappers → MapReduce overhead increases
- Query becomes slow because of excessive task launch overhead
- Solution: use CONCATENATE command to merge small files, or use ORC/Parquet format

### Where is Metadata Stored in Hive?

- Metadata (table definitions, schemas, partition info) → Metastore database (MySQL/Derby)
- Actual data → HDFS
- Common mistake in viva: saying metadata is in HDFS — it is NOT, it is in the relational database backing Metastore

## SECTION 3 — Database and Table Operations

### Create and Use Database

```sql
-- Create a database
CREATE DATABASE college;

-- Use the database
USE college;

-- Show all databases
SHOW DATABASES;

-- Drop database
DROP DATABASE college;

-- Drop database even if it has tables
DROP DATABASE college CASCADE;
```

### Managed Table vs External Table

**Managed Table (default):**

- Hive owns the data
- DROP TABLE deletes both metadata AND data from HDFS
- Data stored at: `/user/hive/warehouse/<database>.db/<table>/`

```sql
CREATE TABLE students (
  id INT,
  name STRING,
  age INT,
  marks FLOAT
)
ROW FORMAT DELIMITED
FIELDS TERMINATED BY ','
LINES TERMINATED BY '\n'
STORED AS TEXTFILE;
```

**External Table:**

- Hive does NOT own the data
- DROP TABLE deletes only metadata — data stays in HDFS
- Use when data is shared between multiple tools
- You specify the HDFS location

```sql
CREATE EXTERNAL TABLE students_ext (
  id INT,
  name STRING,
  age INT,
  marks FLOAT
)
ROW FORMAT DELIMITED
FIELDS TERMINATED BY ','
LOCATION '/user/data/students/';
```

### Show and Describe Tables

```sql
-- List all tables
SHOW TABLES;

-- Show table structure (column names + types)
DESCRIBE students;

-- Show detailed info including location, storage format
DESCRIBE FORMATTED students;

-- Show create statement
SHOW CREATE TABLE students;
```

### Alter Table

```sql
-- Rename table
ALTER TABLE students RENAME TO learners;

-- Add a new column
ALTER TABLE students ADD COLUMNS (email STRING);

-- Change column name and type
ALTER TABLE students CHANGE name full_name STRING;

-- Drop a column (replace all columns — redefine entire schema)
ALTER TABLE students REPLACE COLUMNS (id INT, full_name STRING);
```

### Drop Table

```sql
-- Drop managed table (deletes data too)
DROP TABLE students;

-- Drop external table (keeps data in HDFS)
DROP TABLE students_ext;
```

## SECTION 5 — HiveQL Query Operations

### Basic SELECT

```sql
-- Select all columns
SELECT * FROM students;

-- Select specific columns
SELECT name, marks FROM students;

-- Select with alias
SELECT name AS student_name, marks AS score FROM students;

-- Limit rows
SELECT * FROM students LIMIT 5;
```

### WHERE Clause

```sql
-- Filter rows
SELECT * FROM students WHERE marks > 60;

-- Multiple conditions
SELECT * FROM students WHERE marks > 60 AND age < 22;

-- Like pattern match
SELECT * FROM students WHERE name LIKE 'A%';

-- IN operator
SELECT * FROM students WHERE age IN (20, 21, 22);

-- BETWEEN
SELECT * FROM students WHERE marks BETWEEN 50 AND 80;
```

### GROUP BY

```sql
-- Count students per age group
SELECT age, COUNT(*) AS total
FROM students
GROUP BY age;

-- Average marks per age
SELECT age, AVG(marks) AS avg_marks
FROM students
GROUP BY age;
```

**Important:** Every column in SELECT that is NOT an aggregate function MUST be in GROUP BY.

### HAVING (filter after GROUP BY)

```sql
-- Show only age groups with more than 5 students
SELECT age, COUNT(*) AS total
FROM students
GROUP BY age
HAVING COUNT(*) > 5;
```

**WHERE vs HAVING:**

- WHERE filters rows BEFORE grouping
- HAVING filters groups AFTER GROUP BY

### ORDER BY vs SORT BY

```sql
-- ORDER BY: global sort (single reducer) — all data sorted together
SELECT * FROM students ORDER BY marks DESC;

-- SORT BY: local sort per reducer — faster but only sorted within each reducer
SELECT * FROM students SORT BY marks DESC;
```

### Aggregate Functions

```sql
SELECT
  COUNT(*) AS total_students,
  SUM(marks) AS total_marks,
  AVG(marks) AS average_marks,
  MAX(marks) AS highest,
  MIN(marks) AS lowest
FROM students;
```

## SECTION 6 — Hive Joins

### Setup — Two Tables for Join Examples

```sql
-- Table 1: students
CREATE TABLE students (
  id INT,
  name STRING,
  dept_id INT
)
ROW FORMAT DELIMITED
FIELDS TERMINATED BY ','
STORED AS TEXTFILE;

-- Table 2: departments
CREATE TABLE departments (
  dept_id INT,
  dept_name STRING
)
ROW FORMAT DELIMITED
FIELDS TERMINATED BY ','
STORED AS TEXTFILE;

-- Insert sample data
INSERT INTO students VALUES (1, 'Himanshu', 10);
INSERT INTO students VALUES (2, 'Ravi', 20);
INSERT INTO students VALUES (3, 'Priya', 10);
INSERT INTO students VALUES (4, 'Karan', 99);  -- dept 99 does not exist

INSERT INTO departments VALUES (10, 'Computer Science');
INSERT INTO departments VALUES (20, 'Electronics');
INSERT INTO departments VALUES (30, 'Mechanical');    -- no student in this dept
```

### INNER JOIN

- Returns only rows where condition matches in BOTH tables
- Non-matching rows from either side are excluded

```sql
SELECT s.id, s.name, d.dept_name
FROM students s
INNER JOIN departments d
ON s.dept_id = d.dept_id;
```

Result: Himanshu, Ravi, Priya (Karan excluded — dept 99 not in departments)

### LEFT OUTER JOIN (Most Important — in syllabus)

- Returns ALL rows from LEFT table
- Matching rows from RIGHT table, NULL where no match

```sql
SELECT s.id, s.name, d.dept_name
FROM students s
LEFT OUTER JOIN departments d
ON s.dept_id = d.dept_id;
```

Result: All 4 students returned. Karan gets NULL for dept_name.

### RIGHT OUTER JOIN

- Returns ALL rows from RIGHT table
- Matching rows from LEFT table, NULL where no match

```sql
SELECT s.id, s.name, d.dept_name
FROM students s
RIGHT OUTER JOIN departments d
ON s.dept_id = d.dept_id;
```

Result: All 3 departments returned. Mechanical gets NULL for student columns.

### FULL OUTER JOIN

- Returns ALL rows from BOTH tables
- NULL on side where no match

```sql
SELECT s.id, s.name, d.dept_name
FROM students s
FULL OUTER JOIN departments d
ON s.dept_id = d.dept_id;
```

Result: All students + all departments. Karan gets NULL dept, Mechanical gets NULL student.

### CROSS JOIN

- Returns cartesian product — every row of left × every row of right
- No ON condition
- Dangerous with large tables (4 students × 3 departments = 12 rows)

```sql
SELECT s.name, d.dept_name
FROM students s
CROSS JOIN departments d;
```

### Joins Summary Table (Viva)

|Join Type|Returns|
|---|---|
|INNER JOIN|Only matching rows from both tables|
|LEFT OUTER JOIN|All rows from left + matching from right|
|RIGHT OUTER JOIN|All rows from right + matching from left|
|FULL OUTER JOIN|All rows from both tables|
|CROSS JOIN|Every combination of both tables|

## SECTION 7 — Hive Partitioning

### What is Partitioning?

- Divides table data into separate subdirectories on HDFS based on column value
- Each unique value of the partition column = one subdirectory
- When you query with WHERE on partition column → only that subdirectory is scanned (partition pruning)
- Without partitioning: full table scan every query

### Why Partitioning?

- Performance: avoids reading irrelevant data
- Example: sales table with 5 years of data, query for 2023 only → only reads 2023 directory
- Massive I/O reduction

### HDFS Structure After Partitioning

```
/user/hive/warehouse/college.db/sales/
    year=2021/
        000000_0
    year=2022/
        000000_0
    year=2023/
        000000_0
```

### Create Partitioned Table

```sql
CREATE TABLE sales (
  id INT,
  product STRING,
  amount FLOAT
)
PARTITIONED BY (year INT)
ROW FORMAT DELIMITED
FIELDS TERMINATED BY ','
STORED AS TEXTFILE;
```

**Note:** Partition column (year) is NOT included in the main column list. It is defined separately in PARTITIONED BY.

### Static Partitioning

User manually specifies which partition to load into.

```sql
-- Load data into year=2023 partition
LOAD DATA LOCAL INPATH '/tmp/sales2023.csv'
INTO TABLE sales
PARTITION (year=2023);

-- Load data into year=2022 partition
LOAD DATA LOCAL INPATH '/tmp/sales2022.csv'
INTO TABLE sales
PARTITION (year=2022);
```

**When to use:** When you know the partition value at load time.

### Dynamic Partitioning

Hive automatically determines partition value from the data itself.

```sql
-- Enable dynamic partitioning (must set these first)
SET hive.exec.dynamic.partition = true;
SET hive.exec.dynamic.partition.mode = nonstrict;

-- Source table (all years mixed together)
CREATE TABLE sales_raw (
  id INT,
  product STRING,
  amount FLOAT,
  year INT
)
ROW FORMAT DELIMITED
FIELDS TERMINATED BY ','
STORED AS TEXTFILE;

LOAD DATA LOCAL INPATH '/tmp/sales_all.csv' INTO TABLE sales_raw;

-- Insert into partitioned table dynamically
INSERT INTO TABLE sales PARTITION (year)
SELECT id, product, amount, year FROM sales_raw;
```

Hive reads the `year` column value from each row and automatically creates/fills the correct partition directory.

### Static vs Dynamic Partitioning (Viva Question)

|Feature|Static|Dynamic|
|---|---|---|
|Partition value|User specifies manually|Hive determines from data|
|Speed|Faster|Slower (Hive must scan data)|
|Use case|Single known partition|Multiple partitions at once|
|Risk|Wrong partition if user makes mistake|None|
|MapReduce job|No (just file move)|Yes (data is processed)|

### Query with Partition Pruning

```sql
-- This only reads year=2023 directory — fast
SELECT * FROM sales WHERE year = 2023;

-- Show all partitions of a table
SHOW PARTITIONS sales;

-- Add partition manually (when HDFS data already exists)
ALTER TABLE sales ADD PARTITION (year=2024)
LOCATION '/user/hive/warehouse/college.db/sales/year=2024';

-- Drop a specific partition
ALTER TABLE sales DROP PARTITION (year=2021);
```

## SECTION 8 — Hive Bucketing

### What is Bucketing?

- Divides data within a partition (or table) into a fixed number of files called buckets
- Uses hash(column_value) % number_of_buckets to assign rows to buckets
- Each bucket = one file in the HDFS directory

### Why Bucketing?

- Efficient joins: if two tables bucketed on same column with same bucket count → map-side join possible (no shuffle needed)
- Efficient sampling: read only bucket 1 out of 32 → get representative 3% sample
- More uniform data distribution than partitioning

### Where are Buckets Created? (Viva Question)

- Buckets are created as files inside the table/partition directory on HDFS
- Example for table `employees` bucketed into 4 buckets:

```
/user/hive/warehouse/college.db/employees/
    000000_0    ← bucket 0
    000001_0    ← bucket 1
    000002_0    ← bucket 2
    000003_0    ← bucket 3
```

- If partitioned AND bucketed:

```
/user/hive/warehouse/college.db/employees/
    dept=CS/
        000000_0
        000001_0
        000002_0
        000003_0
    dept=EC/
        000000_0
        000001_0
        000002_0
        000003_0
```

### Create Bucketed Table

```sql
CREATE TABLE employees (
  emp_id INT,
  name STRING,
  salary FLOAT,
  dept STRING
)
CLUSTERED BY (emp_id) INTO 4 BUCKETS
ROW FORMAT DELIMITED
FIELDS TERMINATED BY ','
STORED AS TEXTFILE;
```

### Load Data into Bucketed Table

```sql
-- Enable bucketing enforcement
SET hive.enforce.bucketing = true;

-- Must use INSERT SELECT — LOAD DATA does not respect bucketing
INSERT INTO TABLE employees
SELECT * FROM employees_raw;
```

**Important:** You CANNOT use LOAD DATA for bucketing. You must use INSERT INTO with SELECT because Hive needs to run MapReduce to hash and distribute rows into correct buckets.

### Partitioning + Bucketing Together

```sql
CREATE TABLE emp_partitioned_bucketed (
  emp_id INT,
  name STRING,
  salary FLOAT
)
PARTITIONED BY (dept STRING)
CLUSTERED BY (emp_id) INTO 4 BUCKETS
ROW FORMAT DELIMITED
FIELDS TERMINATED BY ','
STORED AS TEXTFILE;

SET hive.exec.dynamic.partition = true;
SET hive.exec.dynamic.partition.mode = nonstrict;
SET hive.enforce.bucketing = true;

INSERT INTO TABLE emp_partitioned_bucketed PARTITION (dept)
SELECT emp_id, name, salary, dept FROM employees_raw;
```

### Partitioning vs Bucketing (Viva Question)

|Feature|Partitioning|Bucketing|
|---|---|---|
|Divides data by|Column value|Hash of column value|
|Number of divisions|Dynamic (one per unique value)|Fixed (you define bucket count)|
|Storage|Separate subdirectories|Separate files in same directory|
|Used for|Filtering/pruning queries|Efficient joins and sampling|
|Data loading|LOAD DATA works|Must use INSERT SELECT|
|When to use|Column with few distinct values (year, country)|Column with many distinct values (user_id)|

## SECTION 12 — Viva Questions and Answers

**Q1: What is Apache Hive?**

- Data warehouse tool built on top of Hadoop
- Allows querying HDFS data using SQL-like language called HiveQL
- Translates queries into MapReduce/Tez/Spark jobs internally
- Does not store data itself — data lives in HDFS

**Q2: What are the components of Hive architecture?**

- Client (CLI, JDBC, Web UI)
- Driver — manages query lifecycle
- Compiler — parses HiveQL, generates execution plan
- Optimizer — optimizes the plan
- Executor — submits to execution engine
- Metastore — stores metadata in relational DB
- HDFS — stores actual data

**Q3: What is Metastore? Where is it stored?**

- Metastore stores metadata: table names, column names, data types, partition info, HDFS locations
- It is stored in a relational database — MySQL (production) or Derby (default/testing)
- NOT stored in HDFS — metadata is in the relational DB, only actual data is in HDFS

**Q4: What is schema on read?**

- In Hive, schema is NOT enforced when data is written to HDFS
- Schema is applied at query time when data is read
- Advantage: flexible, load raw files without strict validation
- Disadvantage: corrupt/wrong data not detected until query time

**Q5: What is the difference between LOAD DATA and INSERT INTO?**

- LOAD DATA: moves/copies a raw file into Hive warehouse — no MapReduce, no transformation, fast
- INSERT INTO: runs a SELECT query and writes result into table — runs MapReduce, supports transformation

**Q6: What is partitioning? What is its advantage?**

- Divides table data into subdirectories on HDFS based on column values
- Advantage: partition pruning — query reads only relevant partition directory, skipping rest of data
- Massive performance improvement for large tables with filtered queries

**Q7: What is the difference between static and dynamic partitioning?**

- Static: user manually specifies partition value in LOAD DATA command
- Dynamic: Hive automatically reads partition column value from data and assigns rows to correct partitions
- Dynamic needs: SET hive.exec.dynamic.partition=true and SET hive.exec.dynamic.partition.mode=nonstrict

**Q8: What is bucketing?**

- Divides data into fixed number of files using hash(column) % num_buckets
- Enables efficient map-side joins (no shuffle) when two tables bucketed on same column with same count
- Also enables efficient sampling

**Q9: Where are buckets actually created?**

- As separate files inside the table directory (or partition directory) on HDFS
- Example: 4 buckets = 4 files: 000000_0, 000001_0, 000002_0, 000003_0
- Location: /user/hive/warehouse/<db>.db/<table>/

**Q10: What are the joins available in Hive?**

- INNER JOIN — only matching rows from both tables
- LEFT OUTER JOIN — all rows from left, matching from right (NULL if no match)
- RIGHT OUTER JOIN — all rows from right, matching from left (NULL if no match)
- FULL OUTER JOIN — all rows from both tables
- CROSS JOIN — cartesian product
- LEFT SEMI JOIN — like EXISTS in SQL, returns left rows that have a match in right

**Q11: Why is Hive slower than traditional databases?**

- Every query launches a MapReduce/Tez job — high startup overhead
- No in-memory caching of data by default
- No traditional indexes (full table scan)
- Data on HDFS (distributed) — network overhead
- Designed for throughput on large data, not low-latency single queries

**Q12: What happens when small files increase in Hive?**

- Each small file = one HDFS block = one Mapper task
- Too many Mappers = excessive task scheduling overhead
- NameNode memory overloaded (stores metadata for every block)
- Overall query becomes slower despite small data size
- Fix: use ORC/Parquet format, use CONCATENATE, increase block size

**Q13: What is the difference between ORDER BY and SORT BY in Hive?**

- ORDER BY: global sort, uses single reducer, guarantees total ordering, slow on large data
- SORT BY: sorts within each reducer independently, faster but not globally sorted

**Q14: What is the difference between WHERE and HAVING?**

- WHERE filters individual rows BEFORE grouping
- HAVING filters groups AFTER GROUP BY aggregation
- HAVING can use aggregate functions (COUNT, AVG), WHERE cannot

**Q15: What is the difference between managed and external table?**

- Managed: Hive owns data, DROP TABLE deletes metadata + HDFS data
- External: Hive does not own data, DROP TABLE deletes only metadata, HDFS data stays
- Use external when data is shared between multiple tools or systems

**Q16: What is GROUP BY in Hive?**

- Groups rows with same column values together
- Used with aggregate functions: COUNT, SUM, AVG, MAX, MIN
- Every non-aggregate column in SELECT must appear in GROUP BY

**Q17: What is the default Hive warehouse location?**

- /user/hive/warehouse/
- Each database: /user/hive/warehouse/<db_name>.db/
- Each table: /user/hive/warehouse/<db_name>.db/<table_name>/
