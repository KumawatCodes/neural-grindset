## SECTION 1 — Cassandra Architecture (Viva — Most Asked)

### What is Cassandra?

- Distributed NoSQL database designed for high availability and no single point of failure
- Peer-to-peer architecture — every node is equal, no master, no slave
- Developed at Facebook, open-sourced, now Apache project
- Optimized for write-heavy workloads
- CAP theorem: AP system — Available + Partition Tolerant
- Consistency is tunable per operation

### What Type of Architecture Does Cassandra Follow? (Viva)

- **Peer-to-peer architecture**
- All nodes arranged in a logical ring
- Each node owns a range of token values (via consistent hashing using Murmur3)
- Any node can serve any request — no routing through a master
- No single point of failure — if one node dies, others continue serving

### What is Murmur Hash? (Viva Question)

- Murmur3 is the default partitioner algorithm used in Cassandra
- When a row is written, Cassandra applies Murmur3 hash to the partition key
- The hash produces a token value (64-bit integer)
- Token value determines which node on the ring owns this row
- Why Murmur3: fast, non-cryptographic, produces uniformly distributed tokens
- Uniform distribution = balanced data spread across all nodes

### What Does Partition Key Do? (Viva Question)

- Determines which node in the cluster stores the row
- Cassandra hashes the partition key using Murmur3 → token → node responsible for that token range
- All rows with the same partition key are stored together on the same node
- Partition key design is critical — bad design leads to hot spots (one node overloaded)
- For composite partition key: hash is computed on the combination of both columns

### Gossip Protocol (Viva Question)

- Peer-to-peer communication protocol for sharing cluster state information
- Every node gossips with 1-3 random neighbors every second
- Information gossiped: node status (up/down), load, token ranges, schema version
- Within a few gossip rounds, every node knows the state of every other node
- No central coordinator needed — fully decentralized cluster state management
- HeartbeatState: generation + version (increments every round to detect stale info)
- Enables failure detection: if a node stops gossiping → marked as suspect → then down

### Replication (Viva Question)

- Replication Factor (RF): number of copies of each row stored across the cluster
- RF=3: 3 nodes hold each row (coordinator + 2 replicas clockwise on ring)

**SimpleStrategy:**

- Places replicas on next N nodes clockwise on the ring
- Use ONLY for single datacenter — does not consider rack topology

**NetworkTopologyStrategy:**

- Places replicas considering datacenter and rack
- Ensures replicas spread across different racks within each datacenter
- Recommended for production and multi-datacenter

### Consistency Levels (Viva Question)

|Level|Write requires|Read requires|
|---|---|---|
|ONE|1 replica acknowledges|1 replica responds|
|TWO|2 replicas acknowledge|2 replicas respond|
|QUORUM|Majority (RF/2+1) acknowledge|Majority respond|
|LOCAL_QUORUM|Majority in local DC|Majority in local DC|
|ALL|All replicas acknowledge|All replicas respond|
|ANY|At least 1 (even hinted handoff)|Not valid for reads|

**Which consistency level provides highest consistency? → ALL (Viva Answer)**

- ALL requires every replica to respond — strongest consistency, highest latency
- QUORUM is the balanced choice — consistency + availability

**Tunable Consistency Rule:**

- Write CL + Read CL > Replication Factor = Strong consistency guaranteed
- Example: QUORUM write + QUORUM read with RF=3 → 2+2=4 > 3 ✓

### Cassandra Write Path (Per Node)

1. Client sends write to Coordinator (any node)
2. Coordinator determines replica nodes using Murmur3 hash + ring topology
3. Coordinator forwards write to replica nodes in parallel
4. Each replica node:
    - Writes to **CommitLog** first (sequential disk write — durability)
    - Writes to **MemTable** (in-memory sorted structure)
5. Coordinator waits for acknowledgments based on consistency level
6. Returns success to client
7. Background: when MemTable full → flushed to **SSTable** on disk

### Cassandra Read Path

1. Client sends read to Coordinator
2. Coordinator contacts replica nodes based on consistency level
3. Each contacted replica:
    - Checks **MemTable** (most recent data)
    - Checks **Row Cache** (if enabled)
    - Checks **Bloom Filter** (probabilistic: is this key in this SSTable?)
    - Checks SSTable index → reads SSTable
4. Coordinator compares results → returns latest version (by timestamp)
5. If replicas have different data → **Read Repair** (background sync of stale replica)

### Compaction

- Multiple SSTables accumulate over time as MemTables flush
- Compaction merges SSTables: removes tombstones (deleted records), keeps latest version
- Reduces number of SSTables → faster reads (fewer files to check)
- Strategies:
    - **SizeTieredCompactionStrategy** — default, good for write-heavy workloads
    - **LeveledCompactionStrategy** — good for read-heavy workloads
    - **TimeWindowCompactionStrategy** — good for time-series data

## SECTION 2 — Cassandra Data Model (Viva)

### Hierarchy

```
Cluster
  └── Keyspace  (like a database — holds replication config)
        └── Table
              └── Row
                    ├── Partition Key  (determines node — required)
                    ├── Clustering Columns  (determines sort order within partition)
                    └── Regular Columns  (actual data)
```

### Primary Key Components

**Simple Primary Key:**

```sql
PRIMARY KEY (user_id)
-- user_id is both partition key and the only key
```

**Composite Primary Key (Viva — most asked):**

```sql
PRIMARY KEY (user_id, created_at)
-- user_id = partition key (determines node)
-- created_at = clustering column (determines sort order within partition)
```

**Compound Partition Key:**

```sql
PRIMARY KEY ((country, city), user_id)
-- (country, city) together = partition key (hashed together)
-- user_id = clustering column
```

### Is Primary Key Only for Uniqueness? (Viva Question)

- **No** — primary key in Cassandra serves multiple purposes:
    1. **Uniqueness**: identifies a row (like RDBMS)
    2. **Data distribution**: partition key part is hashed to determine which node stores the data
    3. **Data ordering**: clustering column part determines physical sort order of rows within a partition
    4. **Query routing**: Cassandra can only efficiently query by primary key components

### What Do Clustering Columns Do? (Viva Question)

- Determine the **physical sort order** of rows within a partition
- All rows with same partition key are stored together, sorted by clustering columns
- Default clustering order: **ASC (ascending)**
- Can be changed: `WITH CLUSTERING ORDER BY (column DESC)`
- Enable efficient range queries within a partition: WHERE partition_key = X AND clustering_col > Y

### Default Clustering Order (Viva Question)

- **ASC (Ascending)** — rows within a partition sorted in ascending order of clustering column
- Can be overridden at table creation with `WITH CLUSTERING ORDER BY (col DESC)`

### What are Wide Rows? (Viva Question)

- A "wide row" = one partition key with many clustering column values stored together
- Example: user_id = 'U001' with thousands of timestamps as clustering column
- All rows with same partition key stored on same node in sorted order
- Efficient for: time-series data, messages per user, events per session

### Can Wide Rows Create a Problem? (Viva Question)

- **Yes** — called **partition hotspot** or **large partition problem**
- All data for one partition key stored on ONE node
- If partition is too large → that one node becomes overloaded
- Cassandra recommends keeping partition size under 100MB
- Too many tombstones in a wide row → read performance degrades
- Solution: design partition key to distribute data (e.g. bucket by date: user_id + year_month)

## SECTION 3 — Cassandra Data Types (Viva Question)

### Numeric Types

```
tinyint     — 8-bit signed integer
smallint    — 16-bit signed integer
int         — 32-bit signed integer
bigint      — 64-bit signed integer
varint      — arbitrary precision integer
float       — 32-bit IEEE 754 floating point
double      — 64-bit IEEE 754 floating point
decimal     — variable precision decimal
```

### Text Types

```
text        — UTF-8 encoded string (alias: varchar)
varchar     — same as text
ascii       — ASCII string
```

### Date/Time Types

```
date        — date only (no time): YYYY-MM-DD
time        — time only (no date): HH:MM:SS
timestamp   — date + time + timezone (milliseconds since epoch)
timeuuid    — UUID version 1 — contains timestamp (useful for time ordering)
```

### Boolean and Binary

```
boolean     — true / false
blob        — binary large object (arbitrary bytes)
```

### UUID Types

```
uuid        — universally unique identifier (version 4 — random)
timeuuid    — UUID version 1 — embeds timestamp — useful as unique time-ordered key
```

### Network

```
inet        — IPv4 or IPv6 address
```

### Collection Types (Viva — Which Collections Does Cassandra Support?)

- Cassandra supports 3 collection types:

```
list<type>    — ordered collection, duplicates allowed
              — Example: list<text>  → ['apple', 'banana', 'apple']

set<type>     — unordered collection, no duplicates
              — Example: set<text>   → {'apple', 'banana', 'mango'}

map<key,val>  — key-value pairs, keys unique
              — Example: map<text,int> → {'math': 85, 'science': 90}
```

### Frozen Collections

- `frozen<list<text>>` — entire collection stored as single blob, cannot update individual elements
- Required when collection is used inside another collection or as primary key

### Counter

```
counter     — 64-bit integer that can only be incremented/decremented
            — Special table: all non-key columns must be counter type
```

### Create Table — Composite Primary Key (Exam Question)

**Two primary keys: one partition key + one clustering column**

```sql
CREATE TABLE student_marks (
  student_id  INT,
  subject     TEXT,
  marks       FLOAT,
  grade       TEXT,
  PRIMARY KEY (student_id, subject)
  -- student_id = partition key (determines node)
  -- subject    = clustering column (sort order within partition)
);
```

**Compound partition key (both columns together form partition key):**

```sql
CREATE TABLE attendance (
  dept        TEXT,
  student_id  INT,
  date        DATE,
  status      TEXT,
  PRIMARY KEY ((dept, student_id), date)
  -- (dept, student_id) = composite partition key — hashed TOGETHER
  -- date = clustering column
);
```

**With explicit clustering order:**

```sql
CREATE TABLE events (
  user_id     TEXT,
  event_time  TIMESTAMP,
  event_type  TEXT,
  details     TEXT,
  PRIMARY KEY (user_id, event_time)
) WITH CLUSTERING ORDER BY (event_time DESC);
-- most recent events returned first within each user partition
```

### SELECT Queries

```sql
-- Select all rows (full table scan — avoid in production)
SELECT * FROM student_marks;

-- Select specific columns
SELECT student_id, subject, marks FROM student_marks;

-- Select by partition key (efficient — routed to specific node)
SELECT * FROM student_marks WHERE student_id = 1;

-- Select by partition key + clustering column (range query)
SELECT * FROM student_marks WHERE student_id = 1 AND subject = 'Math';

-- Select with ORDER BY (only on clustering column, within same partition)
SELECT * FROM student_marks
WHERE student_id = 1
ORDER BY subject ASC;

-- Limit rows
SELECT * FROM student_marks LIMIT 3;

-- Count rows
SELECT COUNT(*) FROM student_marks;

-- Select with token (advanced — see which node owns a partition)
SELECT token(student_id), student_id FROM student_marks;
```

### ALLOW FILTERING (Exam + Viva Question)

**What is ALLOW FILTERING?**

- Allows queries that filter on non-primary-key columns
- Without it: Cassandra rejects queries that would require full cluster scan

**Why is ALLOW FILTERING not allowed by default? (Viva Question)**

- Cassandra is designed for partition-key-based routing
- Filtering on non-key columns requires scanning ALL partitions on ALL nodes
- Full cluster scan is extremely slow for large datasets
- It defeats the purpose of Cassandra's distributed design
- ALLOW FILTERING explicitly tells Cassandra: "I know this is slow, do it anyway"
- Acceptable only for small tables or development/testing

```sql
-- This FAILS without ALLOW FILTERING
SELECT * FROM student_marks WHERE marks > 80;
-- Error: Cannot execute this query as it might involve data filtering

-- This WORKS with ALLOW FILTERING (but slow on large data)
SELECT * FROM student_marks WHERE marks > 80 ALLOW FILTERING;

-- Filter on grade
SELECT * FROM student_marks WHERE grade = 'A' ALLOW FILTERING;

-- Multiple filter conditions
SELECT * FROM student_marks
WHERE marks > 70 AND grade = 'B'
ALLOW FILTERING;
```

---

### CREATE INDEX (Exam + Viva Question)

**What is Index in Cassandra?**

- Secondary index allows querying by non-primary-key columns WITHOUT ALLOW FILTERING
- Cassandra creates and maintains index automatically in background
- Index stored locally on each node (not a global index)
- Better than ALLOW FILTERING for medium-cardinality columns

**What is the difference between index and ALLOW FILTERING?**

- Index: maintained structure, faster lookups, good for repeated queries on that column
- ALLOW FILTERING: no structure, full scan every time, use only occasionally

```sql
-- Create index on marks column
CREATE INDEX ON student_marks (marks);

-- Create index with a name
CREATE INDEX marks_index ON student_marks (marks);

-- Now query without ALLOW FILTERING
SELECT * FROM student_marks WHERE marks = 85.5;

-- Create index on grade column
CREATE INDEX grade_index ON student_marks (grade);

SELECT * FROM student_marks WHERE grade = 'A';

-- List indexes on a table
DESCRIBE TABLE student_marks;
-- Look for: CREATE INDEX section at bottom

-- Drop an index
DROP INDEX marks_index;
```

**When NOT to use index:**

- High cardinality columns (user_id, email) — too many index entries
- Very low cardinality columns (boolean, status with 2 values) — too many rows per entry
- Best for: medium cardinality (grade, city, department)

## SECTION 8 — Viva Questions and Answers

**Q1: What is Apache Cassandra?**

- Distributed NoSQL database with peer-to-peer architecture
- No master, no slave — every node is equal
- Designed for high availability, fault tolerance, and write-heavy workloads
- CAP: AP system — Available + Partition Tolerant, tunable consistency

**Q2: What type of architecture does Cassandra follow?**

- Peer-to-peer architecture
- All nodes in a logical ring, each owning a token range
- Any node can be coordinator for any request
- No single point of failure

**Q3: What are Cassandra data types?**

- Numeric: tinyint, smallint, int, bigint, float, double, decimal, varint
- Text: text, varchar, ascii
- Date/Time: date, time, timestamp, timeuuid
- Other: boolean, blob, uuid, inet
- Collections: list, set, map
- Special: counter, frozen

**Q4: Which collection types does Cassandra support?**

- **list** — ordered, allows duplicates (e.g. list of phone numbers)
- **set** — unordered, no duplicates (e.g. set of tags)
- **map** — key-value pairs, unique keys (e.g. subject → score)

**Q5: What are wide rows?**

- A partition with one partition key and many clustering column values
- All rows with same partition key stored together on same node sorted by clustering column
- Example: user_id as partition key + event_timestamp as clustering column → one user's entire event history stored together
- Efficient for time-series queries: "get all events for user X between time A and B"

**Q6: Can wide rows create a problem?**

- Yes — large partition problem / hot spot
- All data for one partition key on ONE node — can overload that node
- Partition size recommended under 100MB
- Too many tombstones in wide row degrade read performance
- Fix: add a bucketing column (e.g. year_month) to partition key to spread data

**Q7: What is the default clustering order?**

- **ASC (Ascending)** — rows within a partition sorted in ascending order by clustering column
- Override at table creation: `WITH CLUSTERING ORDER BY (column DESC)`

**Q8: What do clustering columns do?**

- Define physical sort order of rows within a partition
- Enable efficient range queries within a partition (WHERE partition_key = X AND clustering_col > Y)
- Multiple clustering columns: first one is primary sort, second is secondary sort
- Cannot change clustering order after table creation

**Q9: What is Murmur hash?**

- Murmur3 is Cassandra's default partitioner
- Applied to partition key → produces a 64-bit token
- Token determines which node on the ring stores the data
- Chosen for: speed, uniform distribution of tokens across nodes (balanced cluster load)

**Q10: What does partition key do?**

- Determines which node stores the row (hashed with Murmur3 → token → node)
- All rows with same partition key stored on same node
- Foundation of Cassandra's data distribution model
- Bad partition key design = hot spots (uneven data distribution)

**Q11: Is primary key only for uniqueness?**

- No — in Cassandra, primary key serves 3 purposes:
    1. Row uniqueness (like RDBMS)
    2. Data distribution — partition key part determines which node
    3. Data ordering — clustering column part determines sort order within partition
    4. Query routing — only primary key components can be queried efficiently

**Q12: What is gossip protocol?**

- Peer-to-peer protocol for cluster state sharing
- Every node gossips with 1-3 random neighbors every second
- Shares: node status, load, token ownership, schema version
- Within a few rounds, entire cluster has consistent view of all nodes
- Enables failure detection without a central monitor

**Q13: What are the common consistency levels?**

- ONE — fastest, least consistent (1 replica must respond)
- QUORUM — balanced (majority of replicas must respond)
- ALL — strongest consistency, highest latency (all replicas must respond)
- LOCAL_QUORUM — quorum within local datacenter only (for multi-DC)

**Q14: Which consistency level provides highest consistency?**

- **ALL** — requires every replica to acknowledge write or respond to read
- Highest consistency but: if any replica is down → request fails (lower availability)

**Q15: What is ALLOW FILTERING?**

- Allows querying by non-primary-key columns
- Cassandra normally rejects such queries because they require full cluster scan
- ALLOW FILTERING tells Cassandra to scan all partitions on all nodes
- Very slow on large datasets — avoid in production

**Q16: Why is ALLOW FILTERING not allowed by default?**

- Queries without partition key cannot be routed to a specific node
- Cassandra must scan ALL nodes and ALL partitions — O(n) full scan
- Designed for partition-key-based access — full scans defeat distributed design
- On large clusters this can take minutes and put massive load on all nodes

**Q17: What is an index in Cassandra? Difference from ALLOW FILTERING?**

- Secondary index: maintained data structure for fast lookup by non-key column
- Index stored locally on each node for its data
- Faster than ALLOW FILTERING for repeated queries on that column
- ALLOW FILTERING: no structure, full scan every time, slow
- Index: pre-built lookup, faster, but still not as fast as partition key queries
- Avoid index on high-cardinality columns (too many entries) or very low-cardinality

**Q18: Explain the write path in Cassandra**

1. Client → Coordinator (any node)
2. Coordinator hashes partition key → finds replica nodes
3. Writes to all replicas in parallel
4. Each replica: CommitLog first (durability) → then MemTable (memory)
5. Acknowledge back based on consistency level
6. MemTable flushes to SSTable on disk when full

**Q19: Explain the read path in Cassandra**

1. Client → Coordinator
2. Coordinator contacts replicas based on consistency level
3. Each replica: MemTable → Row Cache → Bloom Filter → SSTable index → SSTable
4. Coordinator merges results, returns latest timestamp version
5. Read repair: stale replicas updated in background

**Q20: What is a keyspace in Cassandra?**

- Top-level container (equivalent to database in RDBMS)
- Defines replication strategy (SimpleStrategy or NetworkTopologyStrategy)
- Defines replication factor (how many copies of data)
- All tables inside a keyspace share its replication settings

**Q21: What is a composite primary key? Give an example.**

- Primary key with more than one column
- First column (or group in parentheses) = partition key
- Remaining columns = clustering columns
- Example: `PRIMARY KEY (student_id, subject)` — student_id is partition key, subject is clustering column
- Allows storing multiple subjects per student in same partition, sorted by subject name

**Q22: What is SSTable?**

- Sorted String Table — immutable on-disk file
- Written when MemTable flushes
- Sorted by partition key then clustering columns
- Never modified after written — updates/deletes create new SSTables with tombstones
- Compaction merges multiple SSTables, removes tombstones, keeps latest versions

**Q23: What is a tombstone in Cassandra?**

- Marker written when a row or cell is deleted
- Cassandra does not immediately remove deleted data (SSTables are immutable)
- Tombstone is a special entry indicating deletion with a timestamp
- Physically removed during compaction (after gc_grace_seconds — default 10 days)
- Too many tombstones in a partition → read performance degrades (must scan and skip them)

### Primary Key Patterns

```sql
-- Simple
PRIMARY KEY (id)

-- Composite (partition + 1 clustering)
PRIMARY KEY (user_id, created_at)

-- Compound partition (2 columns hashed together) + clustering
PRIMARY KEY ((country, city), user_id)

-- Multiple clustering columns
PRIMARY KEY (user_id, year, month, day)
```

### Key Architecture Points for Viva (One Line Each)

- Architecture: peer-to-peer ring, no master
- Data distribution: Murmur3 hash of partition key → token → node
- Gossip: every node shares state with neighbors every second
- Replication: RF copies placed on next RF nodes clockwise on ring
- Consistency: tunable per operation — ONE/QUORUM/ALL
- Write: CommitLog → MemTable → SSTable (on flush)
- Read: MemTable → Bloom Filter → SSTable
- Wide row: one partition key + many clustering rows → all on one node
- ALLOW FILTERING: full cluster scan — slow, avoid in production
- Index: local secondary index — better than ALLOW FILTERING for repeated queries
- Compaction: merges SSTables, removes tombstones
